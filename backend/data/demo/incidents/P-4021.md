## Root Cause

1. **Primary:** payment-worker pods OOMKilled after Black Friday–scale traffic spike (marketing email blast not communicated to platform).
2. **Amplifier:** Stripe webhook processor stalled while workers restarted, creating a feedback loop of retries and memory pressure.
3. **Contributing:** Redis connection pool exhaustion on payment-api (max connections 50, burst hit 112).
4. **Organizational:** No documented backup owner for billing DB recovery step; only A. Patel holds prod credentials.

## Exact Resolution Steps

1. Confirmed outage scope via payment-api `/health` and Datadog dashboard `payment-gateway-slo`.
2. Checked Stripe Dashboard → Developers → Webhooks → failed events (last 15 minutes).
3. Ran `kubectl get pods -n prod -l app=payment-worker` — observed OOMKilled status.
4. Executed `kubectl rollout restart deploy/payment-worker -n prod`.
5. When restart insufficient, patched deployment: `kubectl set resources deployment/payment-worker -n prod --limits=memory=1Gi`.
6. Verified `REDIS_URL` on payment-api ConfigMap — increased pool size from 50 → 100 (requires deploy; done via hotfix tag `payment-api:v2.14.1-hotfix`).
7. Manually drained Stripe retry queue via internal admin tool `stripe-replay --since 2024-04-14T09:12:00Z`.
8. Validated billing DB connectivity using prod credentials (sole operator: A. Patel).
9. Ran smoke tests: test charge $0.01, webhook receipt, idempotency key dedup.
10. Posted all-clear in `#incidents` and opened postmortem doc.
